# Word document variants archived as Markdown file variants in git

Removes the tedious and spacious workflow of managing Word document variants as separate documents.
Version management is instead handled by Git within any IDE that has a Markdown editor. 

Yes .docx files are never permanently stored - just edited and then used to re-generate the *same* Markdown file. 
Therefore it can be pushed to the same branch or a new sub-branch with minimal storage needs.
Its full dependency tree as well as its change history log is visible in the IDE, since it understands Git.

New variant maintenance workflow: 
1. Rebase onto the head of each inherited branch that was touched, and validate that the Word documents
are still rendered correctly. 
2. If not, edit the Word documents (or the Markdown file for them) until they do. 
3. Commit and push that final updated Markdown file. 

Now it is up-to-date with any changes in the parent branch and also archived on the server.

No storage space is needed for such rebases because the outdated similar (small) touch-ups will be purged automatically
after a grace period.

## Branch history and direct PDF generation

View the branch history tree from this directory using the prototype in
`../git/contrib/tree` on branch `log-with-branch-history-tree`.
With the CV Python environment active and `typer` installed:

```powershell
python ..\git\contrib\tree\git-tree.py --decorate tree:on:box:supercompact log --all --oneline -- cover_and_cv.md
```

Filtering to `cover_and_cv.md` shows the CV variants with `main` at the
root, excluding unrelated tooling history. Branch labels identify each
branch's latest commit touching this file.
`supercompact` hides intermediate commits, keeping branch tips, branch
points, the root, and HEAD. Omit `-- cover_and_cv.md` for repository-wide
history. Use `--tree` instead of
`--decorate tree:on:box:supercompact` to show every commit.

For Git's built-in summary of branch tips:

```powershell
git log --graph --all --decorate --oneline --simplify-by-decoration
```

Generate PDFs directly, without Word or LibreOffice:

```
python -m pdf
```

This reads `cover_and_cv.md` and writes `Joakim_Pettersson_Cover_Letter.pdf`
and `Joakim_Pettersson_CV.pdf`. Headings are unnumbered, links are clickable,
and pages use A4 with 25 mm side margins and 20 mm top/bottom margins.
The renderer embeds its portable sans-serif font. PyMuPDF is already in
`requirements.txt`; no word processor or additional package is needed.

To choose a source or output directory:

```
python -m pdf cover_and_cv.md --output-dir output
```

## Basic usage

1. Bring up an editor for another variant of [cover_and_cv.md](cover_and_cv.md)
2. Create .docx files when closing it
3. Rebuild [cover_and_cv.md](cover_and_cv.md) from those .docx files

```
git checkout extended
python -m cv
```

## Advanced usage - importing a Hermes App CV

```
python -m cv "Additude - Hermes app.pdf"
```

The file parsers for these .md and .pdf files are currently defined by regex patterns inside cv.py
but the plan is to refactor those into separate .md.fre and .pdf.fre file format files. 

Another plan is that traits now statically defined in HasTraits classes will be autogenerated from the master
.md.fre file that defines how to import an .md file. It will then be possible to have an arbitrary number of such
.md.fre files representing arbitrary documentation structures, and efficiently try them one by one until one matches.
That match test is based just on an autogenerated segmentation of the imported text into subsections, and that is fast
since it uses the regex module for all those matchings and imports.

The parsing of segments takes a little longer since it is looped in python, but still typically well below 0.3 seconds
needed to feel instant. 
That should be pretty scalable, especially if parsing is auto-triggered by Make/CMake or git hooks.
